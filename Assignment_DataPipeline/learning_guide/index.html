What this project actually is

In one sentence: two automated data pipelines that take six messy CSV files from a grocery-delivery company and turn them into clean, trustworthy business reports every morning, on a schedule.

A fictional 10-minute grocery company, NammaMart, ran its daily leadership report by hand in Excel. It was late, full of errors, double-counted money, and leaked customers' phone numbers. The Business Problem

Before any code, understand who the client is and what "done" means to them. This is the real job of a Forward Deployed Engineer.

🏪Who is NammaMart?

NammaMart is a (fictional) 10-minute grocery delivery company in Bengaluru. It runs 15 "dark stores" (small local warehouses) across 4 zones, sells ~150 products, and processed about 2,400 orders in September 2026.

🧨What was broken

😖 The morning that never worked
Every day the COO wanted a 9:30 AM review. An analyst would download five spreadsheets, join them in Excel by hand, and email a summary around 10:30 AM — an hour late. The order totals never matched what the payment gateway said. Duplicate and test orders inflated revenue. Some "10-minute" deliveries showed times of hours. And customers' names, emails, and phone numbers were passed around in plain spreadsheets.

What is a "Forward Deployed Engineer" (FDE)?

An FDE is an engineer who sits with the client, learns their real problem, agrees on what "correct" means, and ships working software on their data. The emphasis is less "write clever code" and more "make the 9 AM number right, explainable, and there every day."

💡 Fact vs Dimension, intuitively
Think of a sentence: "Customer C00199 bought Product P0023 at Store S10 for ₹421.80." The fact is the purchase and its amount. The dimensions are the nouns that describe it — the customer, the product, the store. Facts are what you sum up; dimensions are how you slice and label them.

Core Concepts

The handful of ideas that the whole project is built on. Learn these and nothing else will feel mysterious.

🏭1. What is a data pipeline?

A data pipeline is an automated sequence of steps that moves data from where it is produced (source files, apps, databases) to where it is useful (reports, dashboards), cleaning and reshaping it along the way.

🏭 Like a factory line
Raw material (messy CSVs) enters one end. Each station does one job — unpack, inspect, clean, assemble, package. A finished product (a trustworthy report) comes out the other end. A pipeline is that assembly line, but for data, and it runs itself on a schedule.

2. CSV files

A CSV ("comma-separated values") is a plain-text table: the first line is column names, each following line is a row, values separated by commas. It has no types, no constraints, no indexes — just text.

☕ Coming from MySQL
A CSV is roughly what you'd get if you ran a SELECT * and exported it to a text file — but with none of the guarantees. No column types, no NOT NULL, no primary keys. So a column that should be a number can contain "abc", and a "unique" id can appear twice. That's exactly why the data was so messy and why validation matters.

3. ETL vs ELT — the central idea

Both are pipeline styles. The letters stand for Extract, Transform, Load — the order of the last two is the whole difference.

ETL Clean, then store

Extract → Transform → Load. You clean and validate the data first, in code, and only load the good rows into the warehouse.

  • Bad rows never reach the reporting tables.
  • Finance loves it: the warehouse is always clean.
  • Downside: the original raw rows aren't kept in the warehouse (harder to audit/replay).

ELT Store, then clean

Extract → Load → Transform. You load every raw row first, untouched, then clean it inside the warehouse using SQL.

  • Every original row is kept for audit and replay.
  • Analytics & compliance love it: nothing is ever lost.
  • Downside: bad rows live in the warehouse (must be filtered out carefully).
🍲 A cooking analogy
ETL is washing and chopping the vegetables outside, then bringing only the clean pieces into the kitchen. ELT is bringing the whole basket — dirt and all — into the kitchen, then washing at the sink. Same meal; different place you do the cleaning. ETL keeps the kitchen spotless; ELT keeps every scrap in case you need to check what came in.
✅ Why build both?
The client's CTO was undecided. Finance wanted guaranteed-clean tables (ETL); analytics/compliance wanted every raw record kept (ELT). So you built both on the same data, proved they produce the same numbers, and wrote a recommendation. Proving they match (to the rupee) is what makes the comparison trustworthy.

🔬 Deep dive: why ELT won here, and the historical shift

ETL was born when storage and compute were expensive and warehouses were rigid — you cleaned data before loading because warehouse space and processing were precious. ELT became dominant once cheap, scalable, columnar warehouses (BigQuery, Snowflake, DuckDB) made it feasible to dump everything in and transform with SQL at query-scale.

Concretely in this project: ELT keeps raw_* as an immutable, timestamped copy of every source row, so lineage (tracing a report number back to its exact source rows) is one query. ETL has to reconstruct that from quarantine side-files. As data grows 1000×, ELT's set-based SQL stays fast while ETL's row-wise pandas would strain memory passing whole DataFrames through XCom. That combination — auditability + scalability + ease of change (edit a .sql file, not Python) — is why the recommendation favours ELT, with ETL's strict validation reused as the quality gate.

🏬4. The data warehouse

A data warehouse is a database optimized for analytics (summing, grouping, reporting across lots of rows) rather than for running an app. In this project the warehouse is DuckDB, stored as a single file: warehouse_gaurav.duckdb.

☕ Coming from MySQL
MySQL is built for an application: many small reads/writes, one row at a time (OLTP). A warehouse is built for questions like "total revenue by category for the month" that scan millions of rows (OLAP). Same SQL language you already know — different engine tuned for big aggregations.

5. Star schema (fact + dimensions)

A common warehouse layout: one central fact table (the events — here, orders) surrounded by dimension tables (customer, product, store). Drawn out, it looks like a star.

dim_customer → fact_orders ← dim_product

Queries join the fact to the dimensions: "sum order_amount (fact) grouped by category (product dimension)."

6. Data quality — the six dimensions

"Data quality" isn't vague; it's measured along six concrete dimensions. Every rule in this project maps to one.

DimensionQuestion it answersExample rule here
CompletenessIs required data present?Every order must have a customer_id
UniquenessIs each record stored once?order_id must be unique
ValidityIs the value in the allowed format/list?order_status ∈ {DELIVERED, CANCELLED, RETURNED}
AccuracyIs the value believable?quantity > 0; delivery ≤ 120 min
ConsistencyDoes it agree with other data?Order's product_id exists in products
TimelinessIs the data current?No future-dated order_ts

Each failed check has a severity: Critical rows are quarantined (removed to a side file with a reason); Warning rows still load but are logged.

7. Quarantine

Instead of silently deleting bad rows, the pipeline writes them to a quarantine file with a failure_reason column. Nothing is ever lost without explanation — crucial for audits ("show me the order you rejected and why").

8. Idempotency

Idempotent means running the pipeline twice produces the same result as running it once — no double-counted revenue. Achieved here by rebuilding/replacing tables each run instead of blindly appending.

💡 Like a light switch set to "on"
Flipping a switch to "on" when it's already on changes nothing. An idempotent pipeline is the same: run it again and again, the warehouse ends up in the same correct state. The opposite — appending every run — would keep adding duplicate revenue each time.
🔬 Deep dive: three ways to achieve idempotency

1. Full replace (what ETL's load_star uses): CREATE OR REPLACE TABLE rebuilds the table from scratch each run. Simplest and bullet-proof for modest data, but it rewrites everything even if little changed.

2. Delete-then-insert by key (what the observability tables use): DELETE WHERE run_id = ? then insert this run's rows. Idempotent per run without touching other runs' history — good for append-only audit logs.

3. Upsert / MERGE (the incremental load): match on a key, update if present else insert. Idempotent and efficient for changing data, but the trickiest to get right. At scale you'd prefer (3); for this dataset (1) is clear and correct. Choosing the right one per table is a real design decision, not a default.

9. Incremental load & upsert

The next day's file brings new orders plus corrections to old ones (e.g. an order now RETURNED). An incremental load adds only the new data; an upsert (update-or-insert, also called MERGE) overwrites changed rows and inserts new ones — without creating duplicates.

☕ Coming from MySQL
An upsert is exactly INSERT ... ON DUPLICATE KEY UPDATE in spirit: if the order_id already exists, update it; otherwise insert it. Here it's done by deleting the matching keys then inserting the corrected rows.

10. PII masking

PII = Personally Identifiable Information (names, emails, phones). Masking hides most of it while keeping it usable: priya@example.com → pr***@example.com, 9876543210 → 98******10. We mask rather than delete because reports still need to count customers and rank spend.

11. Orchestration & scheduling

Orchestration is running the steps in the right order, in parallel where possible, with retries and logging. The tool that does this is Apache Airflow (next tab). Scheduling here uses a cron expression — 0 9 * * 1-6 means "09:00, Monday to Saturday."

12. Observability

Being able to tell, from the outside, whether a run was healthy — without reading the code. Done here with a dq_results table (quality scorecard) and a pipeline_runs table (one audit row per run: how many rows in, loaded, quarantined, and the status).

🌬️Apache Airflow

What: a platform to author, schedule, and monitor workflows. A workflow is a DAG (Directed Acyclic Graph) — a set of tasks with dependencies, drawn as boxes and arrows. It shows every run, every task's logs, retries, and status in a web UI.

🎬 Like a film director
Airflow doesn't do the acting (that's your Python/SQL). It's the director: it decides which scenes run in parallel, which wait for others, calls "action" on schedule, re-shoots a scene that fails (retries), and keeps a log of every take.

Why Airflow (not a cron script or Jenkins)? A plain cron + script gives you no visibility, no per-step retries, no dependency graph, no history. Airflow gives all of that plus a UI the client can look at — directly serving the client's "anyone can see whether today's run worked."

⚠️ Key terms
DAG = the whole workflow. Task = one step (a box). TaskFlow API = the modern style where a Python function with a @task decorator becomes a task, and its return value is passed to the next. Trigger = start a run. catchup = whether to back-fill missed schedules (we set it off).

🦆DuckDB

What: an in-process analytical SQL database. The entire warehouse is one file; you query it with standard SQL. Think "SQLite, but built for analytics."

☕ Coming from MySQL
You already know SQL — DuckDB speaks it. The difference: there's no server to install or connect to, no host/port/credentials. You "connect" to a file. And it's tuned for big GROUP BY aggregations (columnar storage) rather than lots of tiny transactions.

Why DuckDB (not Postgres/MySQL/Snowflake)? For a local, open-source assignment it needs zero setup, runs anywhere, and is extremely fast for the aggregate queries a warehouse does. A cloud warehouse (Snowflake/BigQuery) would cost money and need accounts; a server DB (Postgres) would need provisioning. DuckDB is a single pip install and a file.

⚠️ The gotcha we hit
DuckDB allows only one writer at a time and reuses one cursor per connection. That caused two real bugs (a file-lock conflict and an "unfinished result" error) which we fixed by running the write-tasks in a strict sequence and always draining each query's result. Great interview story about debugging.

pandas

What: a Python library for working with tabular data in memory as a DataFrame (a table with typed columns). Used in the ETL pipeline to clean, dedupe, join, and mask.

Why pandas for ETL? It's the standard, expressive tool for row/column manipulation in Python, and ETL cleans data in code before loading. Why not pandas for ELT? ELT cleans inside the warehouse in SQL — and SQL is set-based, scales to huge data, and keeps the logic auditable as .sql files.

Astro CLI (Astronomer)

What: a command-line tool that spins up a complete local Airflow (scheduler, web server, database, etc.) in containers with one command: astro dev start.

Why: installing Airflow by hand is fiddly (many components, a metadata database). Astro packages it so you get a working Airflow in minutes and the exact same setup as everyone else on the course.

Docker / Podman (containers)

What: a container is a lightweight, isolated box holding an app and everything it needs (OS libs, Python, packages). Astro runs Airflow inside containers. Docker and Podman are two engines that run containers; this machine uses Podman.

📦 Like shipping containers
Before standardized shipping containers, loading a ship was chaos. Containers made cargo portable across any ship, crane, or truck. Software containers do the same: the pipeline runs identically on your laptop, a teammate's, or a server — ending "but it works on my machine."

Why it matters here: the DAG file paths like /usr/local/airflow/include/... are paths inside the container. Astro "mounts" your local dags/ and include/ folders into that container so Airflow can see them.

cron & pendulum (scheduling + time zones)

cron is a compact way to express a schedule: 0 9 * * 1-6 = minute 0, hour 9, any day, any month, weekdays 1–6 (Mon–Sat). pendulum is a Python date/time library used to pin the schedule to the Asia/Kolkata time zone so "9 AM" means 9 AM in India, not UTC.

⚠️ The timezone trap
Airflow defaults to UTC. If you don't set the timezone, 0 9 fires at 9 AM UTC = 2:30 PM IST — five and a half hours late for a 9:30 AM meeting. Pinning Asia/Kolkata is what makes the SLA real.

⚠️ The mental model that ties it together
The .py file is a definition, not a script you run top-to-bottom. Astro/containers provide the environment, the scheduler decides when, workers decide what runs next, DuckDB holds the results, and the UI is just a window onto the metadata DB. Separating "define / schedule / execute / store / view" is the whole point of an orchestrator.

The ETL path (clean first)

  1. Extract — five tasks read the five master/daily CSVs in parallel into pandas DataFrames.
  2. Validate — apply the six-dimension quality rules; split each file into passed and failed rows.
  3. Quarantine — write failed rows to a CSV with a failure_reason (nothing silently dropped).
  4. Transform — dedupe dimensions, mask email/phone, join orders to product & store, derive net_revenue, gross_margin, within_15_min.
  5. Load — write a clean star schema (etl_fact_orders + 3 dims) into DuckDB, idempotently (rebuild, don't append).
  6. Reconcile — compare clean orders to payments; write every mismatch with a reason.
  7. Report — build revenue-by-zone and margin-by-category summary tables.
  8. Audit — write a dq_results scorecard and a pipeline_runs row.

The ELT path (store first)

  1. Load raw — copy all five CSVs exactly into raw_* tables (all text, nothing cleaned), tagged with source file + run id.
  2. Stage — SQL files (stg_*.sql) cast types, standardise, dedupe, mask PII, and tag each row with dq_status (PASS/FAIL) + failure_reason.
  3. Incremental MERGE — optionally load the next-day file: append to raw, upsert into staging on order_id.
  4. Mart — SQL files (mart_*.sql) build business-ready tables answering the six questions, reading only dq_status='PASS' rows.
  5. Audit — same dq_results + pipeline_runs tables.

The three ELT layers

LayerTablesRule
Rawraw_orders, …Exact text copy of each CSV. Never cleaned, never deleted.
Stagingstg_orders, …SQL only: cast, standardise, dedupe, mask, mark PASS/FAIL.
Martmart_*SQL only: business-ready answers, clean rows only.
✅ The proof it works
Both pipelines independently produce the same September total revenue — ₹1,133,523.90 — and the same 118 payment mismatches. Identical results from two different designs is what makes the final ETL-vs-ELT recommendation credible.

Why the order of tasks matters

⚠️ Parallel where safe, serial where required
The five extracts run in parallel (they don't touch each other). But every task that writes to DuckDB runs in a strict chain, because DuckDB allows only one writer at a time. Knowing when to parallelise and when to serialise is a core pipeline-design skill.

dags/nammamart_etl_gaurav.py — the ETL pipeline

A single @dag function containing @task functions. Each task is a step; Airflow runs them per the dependencies wired at the bottom.

Key building blocks

  • Helper connect_warehouse() — opens DuckDB with a retry loop, because a write lock can briefly be held by another task. Why: DuckDB is single-writer.
  • Helper run_sql() — runs a statement and always .fetchall()s it. Why: DuckDB reuses one cursor; an un-drained result breaks the next statement.
  • Extract tasks — one per file, run in parallel, each returns the CSV as JSON (how Airflow passes data between tasks, called XCom).
  • validate — calls the shared quality_checks functions; returns passed/failed sets plus the dq_rows scorecard.
  • quarantine — writes failed rows to CSV with failure_reason.
  • transform — numeric casts, dedupe dims, mask PII, join to product/store, derive net_revenue/gross_margin/within_15_min, normalise null zone/category to UNKNOWN.
  • load_star — CREATE OR REPLACE TABLE for fact + 3 dims. Why REPLACE: that's what makes re-runs idempotent.
  • reconcile — left-join payments to clean orders; emit one row per mismatch with a reason.
  • report / write_dq_results / run_audit — summary tables, the quality scorecard, and the run-audit row.
⚠️ Interview-ready detail
The write tasks are wired as a chain (load_star → reconcile → report → write_dq_results → run_audit) specifically so two tasks never hold the DuckDB write-lock at once. run_audit uses trigger_rule="all_done" so it records the run even if an upstream task failed.

dags/nammamart_elt_gaurav.py — the ELT pipeline

  • load_raw — read_csv_auto(..., all_varchar=true) loads each CSV as pure text into raw_*, plus _loaded_at, _source_file, _run_id metadata. Why text: raw must be an exact, lossless copy.
  • stage_dims / stage_orders — run the stg_*.sql files. Dimensions first, because stg_orders joins to them to check consistency.
  • incremental_merge — gated by a DAG param apply_increment (default off, so the baseline matches ETL). Appends to raw, upserts into staging on order_id.
  • build_marts — runs the mart_*.sql files.
  • write_dq_results / run_audit — same observability tables as ETL, keyed by dag_id.
💡 Why a DAG param for the increment?
The assignment needs the baseline September numbers to match ETL exactly. If the increment (October data + corrections) always ran, the totals would differ. So the increment is a switch you flip on only for that specific experiment — baseline stays comparable, and you can still demonstrate the upsert on demand.

include/nammamart/quality_checks.py — the shared "brain"

Pure Python, no Airflow. Each check is a small function returning a boolean mask (True = this row fails), tagged with its dimension and severity. _assemble() combines them: a row is quarantined only if it fails a Critical check; it builds the failure_reason string and the dq_rows scorecard.

✅ Why this design is good
The rules live in one place and are plain functions — so they're unit-testable without Airflow, reusable, and the same logic powers both the pass/fail split (Part A) and the quality scorecard (Part D). Standardisation (fixing upi→UPI) runs before validation, so fixable mess isn't wrongly quarantined.

include/nammamart/masking.py — PII masking

Two small functions: mask_email (keep first 2 chars + domain) and mask_phone (keep first 2 + last 2 digits). Safe on nulls and malformed values. Applied to the customer dimension in ETL; the ELT side does the equivalent in SQL.

⚠️ The bug worth mentioning
Mart joins must filter dq_status='PASS' on the dimension side. Staging flags duplicate products as FAIL but keeps the row; without the filter, joining to the duplicate copy double-counted revenue. Adding AND p.dq_status='PASS' made ELT totals match ETL to the rupee. A clean "two implementations disagreed, here's how I found and fixed it" story.

The ELT side cleans with SQL instead of pandas. Click through stg_orders.sql to see how.

CREATE OR REPLACE TABLE stg_orders AS WITH deduped AS ( SELECT *, ROW_NUMBER() OVER ( PARTITION BY order_id ORDER BY _loaded_at) AS rn FROM raw_orders ), typed AS ( SELECT order_id, TRY_CAST(order_ts AS TIMESTAMP) AS order_ts, TRY_CAST(quantity AS INTEGER) AS quantity, CASE WHEN LOWER(TRIM(payment_mode))='upi' THEN 'UPI' ... END AS payment_mode, CASE WHEN UPPER(TRIM(order_status)) IN (...) THEN UPPER(TRIM(order_status)) ELSE TRIM(order_status) END AS order_status, ... FROM deduped WHERE rn = 1 ), checked AS ( SELECT t.*, CAST(t.order_ts AS DATE) AS order_date, NULLIF(TRIM(CONCAT_WS(';', CASE WHEN t.customer_id IS NULL THEN 'customer_id_missing' END, CASE WHEN t.quantity <= 0 THEN 'quantity_non_positive' END, CASE WHEN c.customer_id IS NULL THEN 'customer_not_in_master' END, ... )), '') AS failure_reason FROM typed t LEFT JOIN stg_customers c ON t.customer_id=c.customer_id AND c.dq_status='PASS' ... ) SELECT *, CASE WHEN failure_reason IS NULL THEN 'PASS' ELSE 'FAIL' END AS dq_status FROM checked;

include/profiling/ — the helper scripts

  • profile_data.py — Part 0 data profiling: row counts, nulls, duplicates, ranges, referential-integrity and business-rule checks. Run before writing pipeline code (the real FDE first step).
  • inspect_warehouse.py — read-only peek at the warehouse tables and counts.
  • test_logic_local.py — runs the quality/masking logic locally (no Airflow) to catch bugs fast.
  • test_elt_sql.py — dry-runs the ELT SQL in an in-memory DuckDB and compares totals to ETL.
  • submission_queries.py — prints the dq_results / pipeline_runs / reconciliation tables and the six business answers for screenshots.

🎯How to talk about this project (resume & interview)

🎯 A 30-second pitch
"I built two production-style data pipelines in Apache Airflow — one ETL (pandas) and one ELT (SQL in DuckDB) — on the same messy retail data. I implemented six-dimension data-quality checks with quarantine and lineage, PII masking, idempotent loads, an incremental MERGE upsert, and observability tables. I proved both pipelines produce identical results and wrote a recommendation comparing them."
  • If asked about debugging: the DuckDB single-writer lock, the "unfinished result" cursor issue, and the duplicate-product double-count — all found by testing and fixed by understanding the root cause.
  • If asked about design trade-offs: ETL vs ELT (auditability vs clean-tables), why mask instead of delete PII, why the increment is param-gated, parallel vs serial tasks.
  • If asked about data quality: the six dimensions, Critical vs Warning severity, quarantine with failure_reason, and the dq_results scorecard.
